# 商城接入 XGift 自动开通 — 改动方案（修订版）

## 一、需求澄清（重要）

**要的**：买家在商城填 X 用户名 → 付款 → 系统直接把 Premium 开到该账号。
**不要的**：发一枚兑换码，让买家自己去兑换。

这推翻了我上一版方案的核心假设。上一版做的是「发码」，是**多了一个中间环节**。

## 二、技术可行性：完全成立

我核对了 XGift 的实际代码，执行赠送的链路是这样的：

```
checkout.Eligibility(ctx, vault, user, port)
    → 校验 X 用户名真实存在、能接收赠礼，返回 X 内部用户 ID

checkout.RunForRecipient(ctx, vault, user, recipientID, pay=true, port, months)
    → 真正执行赠送（含下单与付款）
```

**关键结论：这两个函数只吃「X 用户名」和「月数」，完全不需要兑换码。**

兑换码在 XGift 里只承担两个职责：
1. **付款凭据** —— 证明这笔钱收过了
2. **幂等锚点** —— 防止同一笔重复赠送

而这两件事，**商城侧本来就有**（商城有订单号、有支付流水、有状态机）。所以对商城这条链路来说，兑换码是**冗余的**。

## 三、方案：XGift 新增「直接开通」接口

### 接口设计

```http
POST /api/partner/provision
Authorization: Bearer <商城密钥>
Content-Type: application/json
Origin: https://xg.teyir.com

{
  "order_id": "商城订单号",      // 幂等键
  "username": "x_username",      // 买家的 X 用户名（不含 @）
  "months": 6,                   // 3 或 6
  "reference": "买家备注"
}
```

返回：

```json
{
  "order_id": "...",
  "username": "...",
  "months": 6,
  "status": "succeeded",          // succeeded / processing / review
  "message": "…",
  "progress": 100
}
```

### 与发码接口的本质区别

| 对比项 | 发码（已做的） | 直接开通（你真正要的） |
|---|---|---|
| 输入 | 订单号 + 月数 | 订单号 + **X 用户名** + 月数 |
| 输出 | 一枚兑换码 | **开通结果** |
| 谁完成开通 | 买家自己去兑换 | **系统自动完成** |
| 用户操作 | 还要去另一个站点操作 | **什么都不用做** |
| 兑换码 | 需要 | **完全不需要** |

### 实现要点

这个接口内部**不做发码**，而是直接调用上面那两个函数，逻辑与 `redeem()` 几乎一致，差别只在于：
- 兑换码 → 换成商城的 `order_id`
- `months` 从兑换码记录读 → 从请求参数读

幂等锚点从 `codes` 表挪到新建的 `partner_orders` 表（这个表我上一版已经建好了，可以直接复用）。

**重要：赠送是异步长任务**（要下单、付款、等结果，可能几分钟）。所以接口要支持：
- 首次调用 → 触发开通，返回 `processing`
- 商城轮询同一个 `order_id` → 返回当前进度
- 这样商城侧才知道「开通成功了没」，才能决定要不要发邮件给买家

## 四、商城侧改动

### 商城已经有的（零改动）

商城商品体系里**本来就支持「要求买家填写账号」**：

- `products.require_credentials` —— 勾选后，结账时买家必须填账号
- 买家填的内容加密存到 `product_orders.buyer_account_enc`
- 有专门的解密函数供后台查看

**这正好就是「填 X 用户名」的载体。** 不需要新加字段。

另外商城已有 `require_custom_input`（自定义信息），如果想把「X 用户名」和「账号密码」分开，也可以用这个。

### 需要改的（4 处）

1. **新增取码模块** → 改名成 `modules/xgift_provision.py`
   负责调 XGift 的 `provision` 接口，支持轮询。

2. **`complete_product_order()` 加分支**（`app.py` 约 397 行）
   新增交付类型 `xgift`：拿买家填的用户名去 XGift 开通。
   - 未完成 → 订单停在 `paid`，记录进度，发告警
   - 已完成 → 标记 `fulfilled`
   - **开通是慢操作，要放在后台线程里跑，不能阻塞支付回调**

3. **后台商品表单加选项**（`app.py` 约 2227 / 2301 行）
   新增交付方式「XGift 自动开通」+ 套餐月数字段。

4. **退款边界**（`app.py` 约 451 行）
   ⚠️ 这里比发码方案**严重得多**：
   - 兑换码还能靠「作废」补救
   - **Premium 是直接开在买家账号上的，开了就开了，撤不回来**
   - 所以必须：退款前**先判断开通状态**，已开通的要**转人工审核**，不能自动退款

## 五、下单流程（用户体验）

```
买家在商城选中「X Premium 6个月」
  ↓
填写自己的 X 用户名（必填）
  ↓
付款
  ↓
商城后台自动调 XGift 开通
  ↓
开通成功 → 订单页显示「已开通」+ 邮件通知买家
```

买家**全程不用去第二个网站**，这就是你要的效果。

## 六、必须先确认的事

### 1. X 用户名谁来填、怎么校验

买家可能填错用户名（填成显示名、填错字母）。填错的后果是**钱花了、开给了陌生人**。

建议：商城侧在下单时**先调一次校验**（XGift 已有 `Eligibility`，可以暴露一个只读的校验接口），确认用户名真实存在再让付款。**这一步强烈建议做**，能挡掉绝大多数错填。

### 2. 退款策略要重新定

你这个需求下，退款风险比发码大得多：
- 兑换码模式：退款 → 作废码 → 钱和货都回来了
- 直接开通模式：**已经开在买家号上了，退不回来**

建议规则：**已成功开通的订单，一律不支持自动退款，转人工。**

### 3. 套餐月数与价格

3 个月、6 个月各一个商品，价格你定。

## 七、改动总览

| 侧 | 改动 | 影响面 |
|---|---|---|
| XGift | 新增 `provision` 接口（含用户名校验接口） | 新增，不动现有逻辑 |
| 商城 | 新增模块 + 主文件 4 处 | 新增类型，不动现有交付 |
